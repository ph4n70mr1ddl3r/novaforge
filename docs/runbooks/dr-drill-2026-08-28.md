   metadata, data, audit, workflow, notification, scheduler, integration, file,

   *Finding: the nightly backup jobs the runbook assumes are not configured on
   the compose stack — no cron, no pg_dump job, no WAL archiving. The drill's
   snapshot was operator-initiated.*

   volume — the runbook's DR instance stand-in.
3. **Restore**: full dump replay — **3 m 07 s**, all 13 databases back, zero errors
   beyond pre-existing roles/databases.
4. **Exit criteria (the runbook's §6 list, verified on the restored instance)**:
   - published apps: **all 5** present with versions (Aaa-journey v1, ArDesk v2,
     Erp v5, PerfHook v1, Purchasing v1);

     (JournalEntry 177, Account 168, …) — count-exact vs the source;

5. **RPO achieved**: snapshot-granular (the dump's capture instant, ~1 min of

   this drill**, but only because the drill's own snapshot was the RPO boundary.

## Configured-state findings (the gaps the drill exists to surface)

| # | Finding | Severity | Disposition |
|---|---------|----------|-------------|
| D-1 | **WAL archiving off** (`archive_mode=off`) — PITR (the runbook's ≤5 min RPO mechanism) is impossible as configured; restore granularity = nightly snapshot | high | backlog: enable `archive_mode` + `archive_command` on the compose postgres (a volume for the WAL archive), document the PITR restore |
| D-2 | **Nightly jobs absent** — no pg_dump cron, no Keycloak realm-export schedule | high | backlog: a compose sidecar or host cron per the runbook's table |
| D-3 | **MinIO bucket `novaforge-attachments` is un-versioned** — object overwrite/delete is unrecoverable | medium | backlog: `mc version enable` + the replication leg |
| D-4 | **Kafka topics carry default retention** (7 d broker default — matches the runbook's sizing, but implicit) | low | accept: pin `retention.ms` explicitly per topic |
| D-5 | The compose **`dr` profile referenced by the runbook does not exist** in `novaforge.yaml` | medium | backlog: add the profile (dr-postgres + dr-minio) so the drill is one command |

The secrets-rotation leg (§8) is covered by `IntegrationWebhookTests`' rotation
cases (two-active-window verify → retire → exactly-one-active), re-run in CI;
a live rotation on this stack would rotate the demo `bankFeedKey` — deferred to
the D-2 nightly-job landing so the rotation rides the same operational surface.
