# BuildRight Depot Portfolio — the product dogfood

> **This is not the Phase 7 acceptance dogfood.** `apps/erp` stays exactly what
> PLAN.md's north-star pinned: the mini-ERP that proves the platform, suite-gated
> and version-frozen as the platform's regression corpus. This portfolio is the
> **product deployment** — the BuildRight Depot Corp. model company
> ([github.com/ph4n70mr1ddl3r/erpplans](https://github.com/ph4n70mr1ddl3r/erpplans))
> implemented as a growing family of NovaForge apps, where the platform's pillars
> earn their keep against real domain breadth. Specified by
> [PHASE-7 §12](../../docs/specs/PHASE-7-ERP-DOGFOOD.md) and executed as PLAN.md
> §5's Phase 9; this README restates the contract, the specs govern.

## Portfolio rules

1. **Two-layer dogfooding.** The platform acceptance test (Phase 7, `apps/erp`)
   stays small and green forever. The portfolio apps are where new *platform
   work* is forced by *domain pressure* — and every such forcing is logged in
   this app's gap log (`GAP-LOG.md` + the `gapLog` branch) before any workaround,
   the discipline PHASE-7 §1 rule 2 pins and §12.2 extends to the portfolio.
2. **Requirements traceability is the definition of done.** Every app artifact
   maps to erpplans requirement IDs through `requirements-coverage/` (generated by
   `scripts/generate-coverage.py` from the erpplans checkout's
   `erp-requirements.md` + the hand-maintained `coverage-map.json`). A wave is
   done when its claimed coverage rows are `covered`/`partial` and pinned by a
   suite — not when the entities exist. The matrix's honesty is CI-gated
   (`BuildrightAppArtifactTests`, per PHASE-7 §12.3).
3. **The workflow register is the breadth contract (§12.3a).** The dogfood is
   bound to all of erpplans' operational workflows: `workflow-coverage/`
   (generated by `scripts/generate-workflow-coverage.py` from the upstream
   workflow corpus + the criticality register + the requirement matrix + this
   app's two hand-maintained maps) puts every one of the 5,449 classified rows
   in exactly one state — **pinned** (the workflow's core cycle executes green
   in the e2e corpus; the entry names the suite file(s)), **partial** (claimed
   requirement, no dedicated pin yet), or **uncovered** (visible;
   wave-attributed where the upstream requirement-workflow matrix links them —
   honestly null where it does not yet). The register's honesty is CI-gated
   (`BuildrightWorkflowRegisterTests`): a pin is only as real as the executable
   that runs it — on the committed register and on the hand-maintained
   `workflow-map.json` alike, and the map may not drift from the register (an
   edit there must ship with its regeneration).
4. **Build order follows erpplans' own criticality register**
   (`workflows/workflow-criticality-classification.md`): Tier 1 value streams
   first. Wave ordering below.
5. **Zero handwritten application code.** Apps are versioned JSON authored
   through the definition APIs, gated by `BuildrightAppArtifactTests` (the exact
   save/compile/suite checks the builder and promotion gate run), same as
   `ErpAppArtifactTests` gates the Phase 7 corpus.
6. **Edge systems stay edges.** Per erpplans'
   `07-methodology/capability-sourcing-and-engineering-model.md`, POS / WMS /
   TMS / WFM are bought best-of-breed edges — the portfolio models them as
   integration metadata (connectors, webhooks, imports), never as entities
   (PHASE-7 §12.5).

## Waves

| Wave | Scope (erpplans anchors) | Status |
|------|--------------------------|--------|
| 1 | **P2P cycle** (VS-15 procure-to-pay; R3 procurement; PUR-*): PO with threshold approval, goods receipts with costing, vendor bills with auto-journal + approval, settlement by posted-payment roll-up, open-bills/spend reporting | **this artifact** |
| 2 | **R2R depth** (VS-17 record-to-report; R1/R11): fixed assets, intercompany, tax/BIR reporting, consolidation — forces the report join-lowering (Erp G-12) and `allocate` (Erp G-9) platform features | planned |

| 4 | **The long tail** (governance, loss prevention, ESG, services — PHASE-7 §12.4): the remaining uncovered prefixes ride `coverage-map.json`'s wave-4 prefix defaults (HR, CRM, GOV, MER, LP, BCP, RCL, MKT, SRV, INS, HSE, BIA, ESG, WHL, WSL, MNT, HAZ, ENG, REG, PRJ, PROP, AUD today) | planned |
| platform | **Non-functionals** (NFR): platform contracts (PLAN.md §1, IMPLEMENTATION.md), not app metadata — tracked by the platform phases and the perf harness (`apps/perf`), never per-requirement here (the `coverage-map.json` NFR prefix's own wording) | standing |
| edge | POS (R5), WMS (R4), ecommerce (R6): **integration metadata only** — inbound webhooks, scheduled connector pulls, import mappings against the canonical integration map (`data-volumes-and-integrations.md`) | planned |

## Non-negotiables carried over (PLAN.md §1)

Decimal-precision money (never floats), immutable auditable postings
(`freezeOnTerminal`), approval hierarchies and segregation of duties
(the requester's denial at the approval task — §13's `FORBIDDEN` — is
suite-pinned; the pure `SOD_VIOLATION` lives in the Erp reconciliation suite),
gapless document numbering, and — as the
portfolio grows toward erpplans volumes (134M POS lines/yr, ~100 GB/yr,
BIR 10-year retention) — scale and archival hardening becomes the biggest
platform forcing function. That work is *supposed* to be uncomfortable here.

## Layout

```
apps/buildright/
├── README.md                ← this file (portfolio rules, waves)
├── buildright-app.json      ← wave 1 app definition (P2P, self-contained)
├── GAP-LOG.md               ← human-readable gap log (mirrors the gapLog branch)
├── requirements-coverage/
│   ├── coverage.json        ← generated: per-requirement coverage state
│   └── matrix.md            ← generated: human-readable coverage matrix
├── coverage-map.json        ← hand-maintained: requirement → app/status mapping
├── workflow-coverage/
│   ├── coverage.json        ← generated: per-workflow state (all 5,449 rows)
│   └── matrix.md            ← generated: human-readable workflow register
├── workflow-map.json        ← hand-maintained: workflow → suite pin mapping
├── scripts/
│   ├── generate-coverage.py ← regenerates requirements-coverage/ from an erpplans checkout
│   └── generate-workflow-coverage.py ← regenerates workflow-coverage/ (run generate-coverage.py first)
└── suites/                  ← end-to-end workflow tests (ADR-010 metadata suites)
    ├── p2pHappyPath.json           ← full PO → receipt → bill → journal → payment cycle
    ├── p2pApprovalEdges.json       ← threshold branch, SoD self-approval block, reject/resubmit
    └── p2pReceivingBillingEdges.json ← validation gates, terminal freeze, draft-vs-posted
                                       settlement, BR-G-2 pins (receipt-on-draft-PO, overpay)
```

## Running the gates

```
cd services/metadata-service
../../mvnw test -Dtest=BuildrightAppArtifactTests        # save-clean, compile-clean, suite-valid, coverage-honest
../../mvnw test -Dtest=BuildrightWorkflowRegisterTests   # the workflow register's canon + pin gates
python3 apps/buildright/scripts/generate-coverage.py ~/erpplans            # refresh requirements-coverage/
python3 apps/buildright/scripts/generate-workflow-coverage.py ~/erpplans   # refresh workflow-coverage/ (after the above)
```

**When do the suites actually execute?** Per ADR-010 §4, a change set can only
be promoted with a recorded green run: the Metadata Service drives the suite
through the `TestRunner` against a published candidate in a scratch tenant —
the real runtime, workflow, reporting, and integration surfaces, the real
write path. CI (this artifact test) gates the artifact statically — the exact
split the Phase 7 corpus established (`ErpAppArtifactTests` gates, promotion
runs). The suites are the executable spec of wave 1; the artifact test pins
that they stay well-formed and reference-resolvable.
